# アイコン作成ガイド

公共測量標準図式の記号から、このリポジトリの SVG アイコンを作る手順。

書式の決まりごとは [SVG 設計基準](svg-design-spec.md) にある。このガイドは「その基準を満たす SVG を、図式からどう起こすか」を扱う。

## 0. 一次資料

| 資料 | 所在 |
|---|---|
| 作業規程の準則 付録7 公共測量標準図式 | https://www.gsi.go.jp/common/000258741.pdf |
| 作業規程の準則（本体） | https://www.gsi.go.jp/gijyutukanri/gijyutukanri41018.html |

以下では上記 PDF をローカルに置いたものを `公共測量標準図式.pdf` と呼ぶ。**159ページ・A4横（841.68 × 595.2 pt）**で、記号の図はラスタ画像ではなくベクターで描かれている。サイズが大きいのでリポジトリには置いていない。

**PDF が要るのは台帳と基準形状を作り直すときだけ**（`extract_symbol_table.py` と `dump_zushiki_geometry.py`）。作図・検証・生成の他の手順は PDF 無しで動く。

### 標準か拡張かの見分け方

自治体の拡張 DM コードは標準図式に載らないので、その自治体の仕様書や納品図面を見る。**7桁のものだけではない。** 豊中市の道路台帳平面図では 4143・4191 のように4桁で、しかも標準コードの空き番に入り込んでいる。

**判定に使うのは [`data/standard-codes.csv`](../data/standard-codes.csv)（453コード）で、`data/symbols.csv`（372コード）ではない。** 準則には表が2つある。

| 表 | 件数 | 中身 | 用途 |
|---|---:|---|---|
| 数値地形図データ取得分類基準表 | 372 | 図式の定義がある記号。データタイプ・取得方法つき | `symbols.csv`。アイコンが要るかの判定 |
| 取得分類コード表（巻末） | 453 | **標準のコード全部。** 注記（81xx/82xx）と「未分類」行を含む | `standard-codes.csv`。標準か拡張かの判定 |

前者は後者の完全な部分集合で、81件足りない。**基準表で判定すると、注記コードを拡張と誤判定する。** 空き番を埋めた拡張（2245・8132 など）は「表の取りこぼし」と見分けがつかないので、必ず453件のほうと突き合わせる。

`extract_symbol_table.py` は実行時に、標準に無いコードのアイコンを一覧で出す。

### 拡張コードのキーは提供元ごとに分ける

**標準コードは全国共通だが、標準から外れた枠は提供元ごとに意味が違う。** 同じ `4191` でも、ある自治体では丸囲みの「水」、別の自治体では別物という状態が起こる。全部を `dm-<コード>` の1つのキー空間に入れると、別の自治体のデータに他所の意匠を当ててしまう。

そこで**拡張DMのアイコンだけ、キーに提供元の区画を挟む**。

```
icons/dm-4132.svg            標準図式。全国共通なので区画なし
icons/dm-toyonaka-4191.svg   拡張DM。豊中市の運用
icons/dm-ext1-9109.svg       拡張DM。提供元が未特定のもの
```

区画名は `data/icons.csv` の `提供元` 列に入れる。ビルドは `sprite-one -i./icons` のままで、ファイル名がそのままスプライトのキーになる。

**区画名は「提供元の枠」であって「提供元の名前」ではない。** 衝突は提供元どうしのあいだで起きるので、別の提供元が別の枠に入りさえすれば正しさは保たれる。名前を公開できるかどうかは別の問題なので、次のように使い分ける。

| 提供元 | 区画名 | 理由 |
|---|---|---|
| 出典を公開できる | 実名（`toyonaka` など） | 豊中市は市が道路台帳平面図DM500のサンプルを無償公開しているので出典を書ける |
| 公開できない・未特定 | 中立なトークン（`ext1` など） | 出所が判明したとき、または公開できると分かったときに区画名だけ改める |

`ext1` は 2026-02-20 の `add road icons` で入った6ファイル（`2245` `9101100` `9101200` `9109` `9303210` `9303220`）。**出所が記録されていない**ため中立な区画に置いている。判明したら改名してよい（標準側のキーには影響しない）。

**拡張を1つの `ext` にまとめてはいけない。** 標準と拡張は分かれるが、2つの自治体がどちらも `4191` を持つ場合に `ext` の中で衝突するので、問題が解決しない。

### 拡張コードは、作る前に「既に同じ形があるか」を見る

**拡張コードのアイコンをすべてこのリポジトリに作るわけではない。** 図面の意匠が既存のアイコンと同じなら追加せず、利用側に既存のキーを指してもらう。同じ絵を別のキーで二重に配らないため。

```
拡張コードを見つけた
  ↓ 図面から意匠を実測して案を1枚描く
  ↓ 既存アイコンと突き合わせる
  ├ 同じ形がある → **追加しない。** 利用側が既存のキーを指す
  └ 無い         → dm-<提供元>-<コード>.svg として追加する
```

```bash
python3 tools/verify_shapes.py --similar 案.svg
```

図式との照合と同じ土俵（インクbboxで正規化し、線幅の差は膨張で吸収）で比べるので、大きさの違いは無視され形だけが効く。判定は次のとおり。

| 判定 | 条件 |
|---|---|
| 同一 | ファイルの内容が完全に一致 |
| 同形 | 比率差2%以下・覆い率いずれも95%以上。**代替できる** |
| 近い | 比率差10%以下・覆い率いずれも85%以上。目視で判断する |

**「近い」で代替してはいけない。** 円＋文字の記号は円が支配的なので、中の字が違っても覆い率が80%前後まで出る（`4161` に対し `3531` 保健所が80.4/76.0、`3527` 博物館が84.2/74.8）。図面が持っている区別を潰さないよう、基準は「図面の実測と一致するか」であって「見た目が近いか」ではない。

#### 実例: 41-91（豊中市）は ㊌ で、41-61 と同一だった

豊中市の道路台帳平面図では拡張コード `4191` が ㊌（丸囲みの「水」）で描かれている。#22 でこの意匠と実測寸法つきの作成指示を受けたが、`--similar` に相当する確認をしたところ、**標準図式の `4161` マンホール（水道）が既に ㊌ そのもの**だった（図式との照合も 4.4 / 90.5 / 90.4 で一致）。

図面は `4161` と `4191` を記号で描き分けていない。意匠の根拠は図面の実測しかないので（図式に `4191` の定義は無い）、二重丸にするなどの差別化は根拠が無く採れない。**図面に無い区別を発明しない。**

そこで `dm-toyonaka-4191.svg` は作らず、利用側が `4191` の地物に `dm-4161` を指す形にした。**どのコードをどのアイコンで代替したかは、そのデータを扱うプロジェクトごとの判断なので、対応と根拠は利用側のプロジェクトに記録してもらう。** このリポジトリは「どんなアイコンが存在するか」だけを持つ。

作成指示を受けても、まずこの確認をしてから着手すること。

## 1. 追加するコードを決める

**不足コードを探す工程は無くなった。** 図式に定義された記号は `data/symbols.csv` に台帳化してあり、アイコンが要るのに無いコードは [点記号カバレッジ](symbol-coverage.md) に一覧で出る。

```bash
python3 tools/gen_symbol_coverage.py   # docs/symbol-coverage.md を再生成
```

系統ごとにまとめて描くと、寸法・線幅の判断を使い回せて効率がよい（`glyph()` の使い回しなど）。ただし**寸法は1件ずつ図式から取る**こと。系統内で共通なのは判断のしかただけで、寸法をコピーすると間違える（41-19 有線柱の架線を41-32 電話柱の値で描いてしまった）。

### 点アイコンにすべきでないコードがある

図式の「データタイプ」欄を必ず見ること。**線（E2）や面（E1）として定義されている地物は、点アイコンを作っても正しい表現にならない。** 台帳の `アイコン対象` 列がこの判定を持っている。

実例: 61-10「被覆」は図式上「線 E2、上縁を4号線・他を2号線で描き、上縁の線には直径0.4mmの半円を2.0mm間隔に付す」と定義されている。静岡市データでは点（E5）が2,542件出現するが、同じコードの線が71,271件・面が25,923件あり、点は少数派だった。この種のコードは点アイコン化を見送り、線・面のスタイル側で表現する。

### 逆に、図式が面でも実データが点で入るコードがある

22-35 雨水桝は図式のデータタイプが面（E1）だけだが、豊中市の道路台帳平面図では方向（E6）で最多のコードになる。この種は `data/symbols-overrides.csv` に根拠つきで登録してアイコン対象に含める。意匠の根拠は図式に無いので、納品図面の実測から起こす。

## 2. 図式を読み取る

図式の「図式」欄には記号の形と **mm 寸法**が、隣の「取得方法」欄には挿入位置（座標点が記号のどこに当たるか）が入っている。

### 2-1. 描画コマンドを直接読む（推奨）

**図式PDFの図はベクターなので、描画コマンドを読めば形が数値で取れる。** 画像から目で読むより速く、確実。基準形状は `data/zushiki-geometry.json` に抜き出してあるので、まずこれを見る。

```python
import json
g = json.load(open('data/zushiki-geometry.json', encoding='utf-8'))
print(g['3504'])   # 名称・ページ・描画要素（op / 線幅 / 座標）
```

作り直すときは図式PDFが要る。

```bash
python3 tools/dump_zushiki_geometry.py 公共測量標準図式.pdf
```

### 2-2. 記号本体と寸法の引出線は線幅で分かれる

図式欄には記号そのものと、寸法を示す補助線が混ざっている。**この2つは線幅で機械的に区別できる。**

| 描画 | 線幅 | アイコンに含めるか |
|---|---|---|
| 記号本体（建物等） | 0.6pt | **含める** |
| 記号本体（小物体） | 0.45pt | **含める** |
| 記号本体（土地利用等） | 0.3pt | **含める** |
| 記号本体（42-55 波浪観測所） | 0.9pt | **含める** |
| 寸法の引出線・寸法線 | 0.15pt（多くは破線） | 含めない |
| 寸法の数字・矢印 | 幅を持たない塗り | 含めない |

これを取り違えると記号の要素を丸ごと落とす。実例: **41-32 電話柱・41-42 電力柱**の図式では円から放射状に線が伸びている。これを引出線と読んで円だけを描いてしまったが、実際は記号本体の線幅で描かれた**架線**だった。線幅で切り分ければこの誤りは起きない。

塗り（`fs` = 塗り＋線）は**塗り色を見る**こと。図式の塗りはほぼ白で、下の線を隠すためのもの。黒く塗ると別形状になる。

### 2-3. 画像として読む場合（補助）

寸法の数字を読むときや、抽出結果を確かめるときは画像で見る。図式欄は全ページ共通で **x ≈ 248〜350 pt**。

```python
import fitz
page = fitz.open('公共測量標準図式.pdf')[64]        # 0起算
pm = page.get_pixmap(clip=fitz.Rect(248, 120, 350, 160), matrix=fitz.Matrix(14, 14))
pm.save('zu.png')
```

細い線を消して本体だけを残したいときは MaxFilter が使える（線幅で切り分けられない場合の代替）。

```python
from PIL import Image, ImageFilter
import numpy as np
solid = np.array(Image.open('zu.png').convert('L').filter(ImageFilter.MaxFilter(11))) < 128
```

### 2-4. 変種の扱い

1つのコードに地図情報レベル別（500/1000/2500/5000）や「真形／極小」など複数の図式が載る。

- 形が同じで寸法だけ違う場合はどちらを見てもよい
- **形が違う場合は簡略な方（極小）を採る** — 小サイズで読めることを優先する
- **真形（実際の外形）は記号ではない。** 41-17 地下換気孔では真形の外枠 6.4×3.1mm を落として中の格子だけを採った
- 変種は縦に並ぶが、**間隔が1pt未満のこともある**（35-08 税関は0.62pt）。位置だけでは切り分けられないので線幅の違いで見分ける

真形や補助線を落とす判断は `verify_shapes.py` の `EXCLUDE` に理由つきで書く。判定が「判断あり」になり、後から検証できる。

## 3. 大きさを決める

mm 寸法をそのまま px に換算すると既存アイコンと揃わない。既存アイコンは形状こそ図式に忠実だが、**大きさは mm 比の厳密再現ではなく、64px キャンバス上で見た目が揃うように描かれている**。

新規アイコンも同じ方針でよい。**形状の縦横比は図式どおりに保ち、絶対サイズは同系統の既存アイコンに合わせる。**

### 系統ごとに倍率を校正する

一律の換算率は使えない。**その系統の既存アイコンについて「図式の実測(pt)」と「アイコンの実測(px)」の比を取り、中央値を使う**のが確実。

| 系統 | 校正した倍率 | 根拠 |
|---|---|---|
| 建物等（35-xx） | 図式実測の最大寸法が**インク22px** | 円が4.0mmで揃っているので、円だけの記号なら既存の3519/3525/3526/3536と同径になる |
| 小物体（42-xx） | **px/pt = 2.0**（22px上限） | 中央値1.95。4101/4111 マンホール1.8・4215 消火栓2.2・4241/4243 灯台・灯標2.3・4132 電話柱2.0 |
| 土地利用等（62-xx / 63-xx） | **px/pt = 1.7**（22px上限） | 中央値1.68。6311 田1.53・6313 畑1.72・6331 広葉樹林1.83・6334 荒地1.62 |

**「最大寸法を22pxに揃える」を全系統に使ってはいけない。** 小物体は1.0mm（有線柱）から6.0mm（ヘリポート）まで幅があり、一律にすると大小の区別が消えるうえ、41-19 有線柱が兄弟の 41-32 電話柱（円9.3px）と揃わなくなる。

図面の実寸に合わせるのは**利用側の `icon-size` の仕事**。スプライト側で小さく描くと図形が潰れる（22-35 雨水桝を4.44pxにすると枠の内側が1px未満になり点になる）。

### 目安の実測値

`tools/inspect_icons.py` で測れる。

| 系統 | 例 | bbox |
|---|---|---|
| 官公署の円 | 3525 / 3526 / 3536 / 3519 | 22.0 × 22.0 |
| 〒などの円 | 3509 | 24.4 × 24.4 |
| 括弧つき文字 | 7201「(土)」/ 7211「(岩)」 | 約 26 × 15 |
| 植生 | 6332 / 6334 / 6337 | 10〜16px 角 |
| 横長の線状記号 | 4207 / 5228 / 4219 | 幅 13〜19・高 4〜5 |
| 小さい点記号 | 2238 | 6.2 × 6.2 |
| 枠だけの小記号 | 2235 | 11.2 × 11.2 |

共通の目安:

- bbox は **10〜22px**（横長の記号は幅がこれを超えることもある）
- 線幅は **約 1.1px**。ただし図式が他より太く描いている記号は図式に合わせる（42-55 波浪観測所は図式が0.9ptで他の倍のため1.8px）
- 中心は **(32, 32)**（`center_ink()` で合わせられる）

## 4. 塗りパスを組み立てる

設計基準どおり、**ストロークは使わず線も塗りパスで表現する**。手で `d` を書くのは現実的でないので `tools/gen_icons.py` のヘルパを使う。

```bash
python3 tools/gen_icons.py            # tools/out_icons/ に書き出す（確認用）
python3 tools/gen_icons.py --install  # icons/ に直接書き出す
```

| ヘルパ | 用途 |
|---|---|
| `seg(p0, p1)` | 直線1本（バットキャップの矩形になる） |
| `polyline([p0, p1, ...])` | 折れ線。頂点はマイター接合され、突き合わせの欠けが出ない |
| `arc_band(cx, cy, r, a0, a1)` | 円弧。角度はラジアン、Y は下向き |
| `ring(cx, cy, r)` | 穴あきの円。外円と内円を逆回りにして nonzero で抜く |
| `glyph(ch, height, cx, cy)` | 漢字などの字形アウトライン（高さで揃える） |
| `glyph_box(ch, size, cx, cy)` | 字面の長辺で揃える。「工」のような横長の字が円からはみ出すのを防ぐ |
| `poly_band([p0, p1, ...])` | 閉じた多角形の輪郭。`polyline()` で始点に戻ると始点だけ接合が効かず形が非対称になる |
| `ellipse_band(cx, cy, rx, ry)` | 楕円の輪郭 |
| `center_ink(d)` | インク外形の中心を (32,32) に合わせる。マイターは尖った頂点で外へ伸びるがバットキャップは伸びないので、寸法どおり組むだけでは0.5pxずれる |
| `trace(items, ink)` | 図式の実測座標をそのままパスに写す（曲線が主体で手で組みにくい記号用）。**照合が自己参照になる**ので目視確認が必須 |

戻り値はいずれもパスデータの文字列なので、`+` で連結して `write(コード, データ, 説明)` に渡すと1パスの SVG になる。

作図例はスクリプト末尾にある。図式から読んだ寸法と、そこから決めた px 値をコメントに残しておくと後から検証できる。

```python
# ---- 72-12 露岩 ----
# 図式: 上に開いた半円（幅1.5mm・深さ0.75mm）＋弦の中央に短い線分（0.5mm）。
# 幅14px とすると半径7px、線分長 14*(0.5/1.5)=4.67px。
w = 14.0
r = w / 2
chord_y = CY - r / 2
bar = w * (0.5 / 1.5)
d = (arc_band(CX, chord_y, r, 0, math.pi) +
     seg((CX - bar / 2, chord_y), (CX + bar / 2, chord_y)))
write('7212', d, '半円＋弦中央の線分')
```

### 方向レイヤ（E6）の記号は右（東）向きに描く

方向レイヤの記号は `Angle` 属性で回転して使う。**角度0＝水平右（東）**が基準なので、記号の軸が水平右を向いた状態で作図する。図式の図はたいてい既にその向きで描かれている。

記号レイヤ（E5）は回転しないので、図式の向きのままでよい。

**回転の軸に注意する。** MapLibre は `icon-anchor` の既定値が中心なので、64px キャンバスの中心 (32,32) が地物の座標に置かれ、そこを軸に `icon-rotate` が効く。記号の「取得位置」（柱の中心・ポールの位置など、図式の取得方法欄に図示されている点）が中心から離れていると、回転させたとき記号全体がその点のまわりを公転してしまう。**取得位置と記号の重心がずれる記号では、取得位置を (32,32) に置く**（41-32 電話柱・41-42 電力柱は円の中心を (32,32) に置いている）。インクの bbox 中心は多少ずれてよい。

同じコードが点 E5 と方向 E6 の両方を持つことがあり（41-32 は方向90件・記号30件）、スプライトは1コードにつき1画像なので、どちらか一方に寄せた作図になる。取得位置を中心に置いておけば、少なくとも位置は両方で合う。

### 字入りの記号

○の中に漢字が入る記号（35-31 保健所など）は、書体のアウトラインを使う。`glyph()` は **Noto Sans JP**（SIL OFL、MIT の本リポジトリと両立する）から字形を取り出し、`transform` 属性を使わずパス座標に焼き込んで1パスにまとめる。

ウェイトは 400 が既存アイコンの線幅（約1.1px）に近い。円の外径 22px に対して字の高さ 12.5px が収まりの目安。

## 5. 検証する

### 図式と見比べる

切り出した図式画像と、作った SVG のレンダリングを並べて確認する。読み取りの手順そのものを検証したいときは、**既にあるアイコンを同じ手順で図式から読み直し、実物と一致するか**を見るとよい（例: 7211 岩がけ = 図式「(岩) 3.5×2.5mm」）。

### 形が図式と一致していることを保証する

目視と寸法の実測だけでは「図式の形と合っているか」の証明にならない。図式から起こした**基準形状をリポジトリに置き**、それとの一致を機械判定する。

```
図式PDF → [抽出・目視レビュー] → data/zushiki-geometry.json
                                     ↓ 毎回の自動判定（PDF不要・CIで実行）
                                 icons/*.svg
```

```bash
python3 tools/verify_shapes.py                    # 全件の数値を出す
python3 tools/verify_shapes.py 6224 --overlay ov.png   # 指定コード＋重ね画像
python3 tools/verify_shapes.py --check            # 基準値と突き合わせ、外れたら終了コード1
python3 tools/verify_shapes.py --write-baseline    # 基準値を書き直す

python3 tools/dump_zushiki_geometry.py 公共測量標準図式.pdf   # 基準形状を作り直す（PDFが要る）
```

基準形状は **図式PDFの描画コマンドのうち記号本体の線幅のものだけ**を抜いたもの。寸法の引出線（0.15pt・多くは破線）・矢印・数字（幅を持たない塗り）は入らない。本体の線幅は大分類ごとに違う。

| 大分類 | 本体の線幅 |
|---|---|
| 建物等（35-xx） | 0.6pt |
| 小物体（42-xx） | 0.45pt |
| 土地利用等（62-xx / 63-xx） | 0.3pt |
| 42-55 波浪観測所だけ | 0.9pt |

出る指標は3つ。

| 指標 | 何が出るか |
|---|---|
| 比率差 | インク外形の縦横比のずれ → 長さ・位置の間違い |
| アイコン→図式 | アイコンのインクが図式側で覆われる割合 → **余分な要素** |
| 図式→アイコン | 図式のインクがアイコン側で覆われる割合 → **欠けた要素** |

絶対寸法と線幅は意図的に図式と違うので、次の2つで揃えてから比べる。

- インク外形の長辺を同じ大きさに正規化する
- **基準画像の線幅をアイコン側と同じ相対太さに引き直す。** これをしないと、尖った頂点でマイターが線幅に比例して伸びる分が数値に出てしまう（税関で比率差8.8%→0.6%になった）

比率差のしきい値を10%にしているのは、図式が三角形などを「3本の別々の線」で描くのに対し、こちらは頂点の欠けを避けてマイター接合する方針のため、尖った角では意図的にインクが外へ伸びるから。覆い率のほうが要素の欠け・余分に敏感なので85%を維持する（41-19 有線柱の架線の誤りは覆い率58.8%で出た）。

#### 比率差の読み方

インク外形の bbox の縦横比を、図式側を分母にして比べた相対誤差（`verify_shapes.py` の `measure()`）。

```
図式のアスペクト比    ta = 図式インクbboxの 幅 / 高
アイコンのアスペクト比 ia = アイコンインクbboxの 幅 / 高
比率差 = |ta - ia| / ta × 100
```

`data/shape-baseline.csv` の数字を額面どおりに読むと誤診するので、3つ注意する。

- **絶対の大きさは見ていない。** 縦横比だけなのでスケール不変。大きさが何倍違っても比率が同じなら0%になる
- **分母が図式側なので非対称に効く。** 図式が平たい／細長い記号は ta が極端な値になり、わずかなずれでも数百%に振れる（52-41 流水方向 460%・22-43 道路標識警戒 642%・52-27 せき 203%）。**値の大きさは間違いの大きさに比例しない**
- **0%は形の一致を意味しない。** bbox の縦横比しか見ないので、中身が違っていても揃う（73-05 公共基準点（水準点）は比率差0.0で覆い率85.1/74.6、81-99 指示点は0.0で60.1/100.0）

形の当否を担っているのは覆い率の2列で、比率差は長さ・位置がおかしくないかの粗いふるい。要確認を1件ずつ見るときは覆い率から読む。

#### 何が保証されるか

- **黙って形を変えられない。** `--check` が `data/shape-baseline.csv` と突き合わせるので、アイコンを変えれば必ず基準値の差分がレビューに出る。CI（`.github/workflows/shape-check.yml`）でも走る
- **判定の区分が1件ずつ記録される。** 基準値の「判定」欄が次のどれかになる

| 判定 | 意味 |
|---|---|
| 一致 | 比率差10%以下・覆い率85%以上。**独立に検証できている** |
| 要確認 | 数値が基準を外れている。基準形状の抽出側の問題か、実際のずれかを1件ずつ見る |
| 字入り | ○＋文字。字形は書体が違う（Noto Sans JP）ので一致しない。円の比率だけが見どころ |
| 座標写し | `trace()` で図式の座標を写した記号。**判定が自己参照になる**ので独立の根拠にならない。目視レビューの結果を根拠欄に残す |
| 確認済 | 数値は基準を外れるが、図式と並べて目視で確認し理由が説明できるもの。理由を `REVIEWED` に書く |
| 判断あり | 図式の一部を除外した（真形の外枠など）。理由を `EXCLUDE_REASON` に書く |
| 図式外 | 図式に点記号の定義が無く、意匠の根拠が図面の実測（22-35 雨水桝など） |
| 検証不可 | 図式が塗りだけで描かれていて基準形状が取れない |

#### つまずきやすいところ

- **`fs`（塗り＋線）の塗り色を見る。** 図式の塗りはほぼ白（下の線を隠すため）で、黒く塗ると別形状になる。塗り色が暗いときだけ塗る
- **変種の切り分け。** 図式欄には500/1000用と2500用が縦に並ぶ。間隔が1pt未満のこともあるので（35-08 税関は0.62pt）、位置だけでは切り分けられない。線幅の違いで見分けて `EXCLUDE` に書く

#### 保証できないこと

- **基準形状そのものの妥当性**は自動判定できない。真形か極小か、どの変種か、どの要素を落とすかは人の判断なので、`data/zushiki-geometry.json` をコミットする時点の目視レビューが唯一の担保
- 絶対寸法・線幅・字形の一致は見ていない（設計方針で意図的に違う）
- 尖った頂点はマイターが線幅に比例して伸びるため、線幅を太くしている分だけ比率差が数%出る

### 数値で確認する

```bash
python3 tools/inspect_icons.py dm-7212            # 個別
python3 tools/inspect_icons.py dm-7212 dm-3525    # 既存と並べて比較
```

bbox・中心・線幅を実測して出す。中心が (32, 32)、線幅が 1.0〜1.3px、bbox が同系統の既存アイコンと同程度なら、基準を満たしている。

### 小さいサイズで見る

実際の表示は 25〜30px 程度になる。その大きさでレンダリングして、潰れていないか確認する。

## 6. 一覧を更新する

名称のマスタは [`data/icons.csv`](../data/icons.csv)（`ファイル名,4桁コード,名称,分類,提供元`）。追加したアイコンの行を足す。分類は `標準図式` / `拡張DM` / `その他`。**拡張DM のときは `提供元` を必ず埋める**（下記）。

コミットしたあとに一覧を再生成する。追加日は git 履歴から取るので、**コミット後に実行する**こと（先に実行すると追加日が `-` のまま入る）。

```bash
git commit ...                        # 先にアイコンをコミットする
python3 tools/gen_icon_list.py        # docs/icon-list.md と README の履歴
python3 tools/gen_symbol_coverage.py  # docs/symbol-coverage.md
python3 tools/verify_shapes.py --write-baseline   # data/shape-baseline.csv
python3 tools/verify_shapes.py --check            # 基準値と合っているか
git commit ...                        # 生成物をコミットする
```

生成物のコミットを忘れると、図には出ないが一覧の追加日が `-` のまま残る。
